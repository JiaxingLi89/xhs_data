        # Format used by MediaCrawler media_platform/xhs/help.py:get_search_id.

    在开始联网操作前，先检查 CDP 模式可用性；已有连接优先复用：
    
    ```bash
    node "${CLAUDE_SKILL_DIR}/scripts/check-deps.mjs"
    ```
    
    **Node.js 22+** 必需（使用原生 WebSocket）。
    
    脚本先读取 `/health`：已有服务且 `connected === true` 时，校验浏览器偏好后直接使用，不重新探测浏览器、不启动第二个 Proxy；已有服务但连接断开时，由原服务重新连接。只有没有可用服务时，才发现浏览器并启动后台 Proxy。
    
    按脚本输出处理：
    - `exit 0` → 直接调用 Proxy API，不再手动启动或重启 Proxy

    ## 浏览哲学与工作流
    
    **像人一样思考，兼顾高效与适应性的完成任务。**
    
    执行任务时不会过度依赖固有印象所规划的步骤，而是带着目标进入，边看边判断，遇到阻碍就解决，发现内容不够就深入——全程围绕「我要达成什么」做决策。这个 skill 的所有行为都应遵循这个逻辑。
    
    **① 拿到请求** — 先明确用户要做什么，定义成功标准：什么算完成了？需要获取什么信息、执行什么操作、达到什么结果？这是后续所有判断的锚点。
    
    **② 选择起点** — 根据任务性质、平台特征、达成条件，选一个最可能直达的方式作为第一步去验证。一次成功当然最好；不成功则在③中调整。比如，需要操作页面、需要登录态、已知静态方式不可达的平台（小红书、微信公众号等）→ 直接 CDP
    
    **③ 过程校验** — 每一步的结果都是证据，不只是成功或失败的二元信号。用结果对照①的成功标准，更新你对目标的判断：路径在推进吗？结果的整体面貌（质量、相关度、量级）是否指向目标可达？发现方向错了立即调整，不在同一个方式上反复重试——搜索没命中不等于"还没找对方法"，也可能是"目标不存在"；API 报错、页面缺少预期元素、重试无改善，都是在告诉你该重新评估方向。遇到弹窗、登录墙等障碍，判断它是否真的挡住了目标：挡住了就处理，没挡住就绕过——内容可能已在页面 DOM 中，交互只是展示手段。
    
    **④ 完成判断** — 对照定义的任务成功标准，确认任务完成后才停止，但也不要过度操作，不为了"完整"而浪费代价。
    
    ## 联网工具选择
    
    - **确保信息的真实性，一手信息优于二手信息**：搜索引擎和聚合平台是信息发现入口。当多次搜索尝试后没有质的改进时，升级到更根本的获取方式：定位一手来源（官网、官方平台、原始页面）。
    
    | 场景 | 工具 |
    |------|------|
    | 搜索摘要或关键词结果，发现信息来源 | **WebSearch** |
    | URL 已知，需要从页面定向提取特定信息 | **WebFetch**（拉取网页内容，由小模型根据 prompt 提取，返回处理后结果） |

    进入浏览器层后，`/eval` 就是你的眼睛和手：
    
    - **看**：用 `/eval` 查询 DOM，发现页面上的链接、按钮、表单、文本内容——相当于「看看这个页面有什么」

    - **读**：用 `/eval` 提取文字内容，判断图片/视频是否承载核心信息——是则提取媒体 URL 定向读取或 `/screenshot` 视觉识别

    ### 页面就绪与完成判断
    
    `/new` 或 `/navigate` 返回，只代表浏览器完成了当前文档的基础加载，不代表用户需要的内容已经出现。HTTP 200、`document.readyState === "complete"`、页面标题出现或导航调用成功，都不能单独作为任务完成标准。
    
    导航后先用 `/eval` 检查目标内容。若目标内容尚未出现，而页面仍是空白、加载态、验证页、登录跳转或其它可能继续变化的中间状态，在默认 15 秒窗口内持续观察 URL、标题和 DOM；页面发生跳转或内容变化后重新判断。只有目标内容已经获取，或观察窗口结束后仍存在明确阻碍，才能继续提取或报告失败。
    
    站点经验可以提供更精确的选择器、等待条件和已知中间状态，但只用于加速判断；即使没有站点经验，也必须遵循上述目标内容就绪规则。

    ### 程序化操作与 GUI 交互
    
    浏览器内操作页面有两种方式：
    
    - **程序化方式**（构造 URL 直接导航、eval 操作 DOM）：成功时速度快、精确，但对网站来说不是正常用户行为，可能触发反爬机制。
    - **GUI 交互**（点击按钮、填写输入框、滚动浏览）：GUI 是为人设计的，网站不会限制正常的 UI 操作，确定性最高，但步骤多、速度慢。
    
    根据对目标平台的了解来灵活选择方式。GUI 交互也是程序化方式的有效探测——通过一次真实交互观察站点的实际行为（URL 模式、必需参数、页面跳转逻辑），为后续程序化操作提供依据；同时当程序化方式受阻时，GUI 交互是可靠的兜底。
    
    **站点内交互产生的链接是可靠的**：通过用户视角中的可交互单元（卡片、条目、按钮）进行的站点内交互，自然到达的 URL 天然携带平台所需的完整上下文。而手动构造的 URL 可能缺失隐式必要参数，导致被拦截、返回错误页面、甚至触发反爬。
    
    ## 浏览器 CDP 模式
    
    通过 CDP Proxy 直连用户日常浏览器（Chrome、Edge、Brave、Arc、Dia 等任意 Chromium 内核浏览器），天然携带登录态，无需启动独立浏览器。
    若无用户明确要求，不主动操作用户已有 tab，所有操作都在自己创建的后台 tab 中进行，保持对用户环境的最小侵入。不关闭用户 tab 的前提下，完成任务后关闭自己创建的 tab，保持环境整洁。
    
    ### 启动
    
    ```bash
    node "${CLAUDE_SKILL_DIR}/scripts/check-deps.mjs"
    ```
    
    脚本检查 Node.js 后先复用已有 Proxy；没有可用服务时才检查浏览器调试端口、自动启动并等待连接。Proxy 以脱离当前命令会话的后台进程持续运行，没有运行时长或空闲退出计时器。前置检查的等待超时只结束本次检查，不停止 Proxy。
    
    `/health` 的 `status: "ok"` 表示服务在运行，`connected: true` 表示浏览器连接仍有效。浏览器退出、重启或撤销远程调试权限后，服务可继续运行，但重新连接可能需要浏览器再次授权；不要把服务存活当成连接有效。

    所有操作通过 curl 调用 HTTP API：

    ### 页面内导航
    
    两种方式打开页面内的链接：
    
    - **`/click`**：在当前 tab 内直接点击用户视角中的可交互单元，简单直接，串行处理。适合需要在同一页面内连续操作的场景，如点击展开、翻页、进入详情等。
    - **`/new` + 完整 URL**：使用目标链接的完整地址（包含所有URL参数），在新 tab 中打开。适合需要同时访问多个页面的场景。
    
    很多网站的链接包含会话相关的参数（如 token），这些参数是正常访问所必需的。提取 URL 时应保留完整地址，不要裁剪或省略参数。URL 通过 POST body 原样传入 `/new` 或 `/navigate`。

    ### 媒体资源提取
    
    判断内容在图片里时，用 `/eval` 从 DOM 直接拿图片 URL，再定向读取——比全页截图精准得多。
    
    ### 技术事实
    - 页面中存在大量已加载但未展示的内容——轮播中非当前帧的图片、折叠区块的文字、懒加载占位元素等，它们存在于 DOM 中但对用户不可见。以数据结构（容器、属性、节点关系）为单位思考，可以直接触达这些内容。
    - DOM 中存在选择器不可跨越的边界（Shadow DOM 的 `shadowRoot`、iframe 的 `contentDocument`等）。eval 递归遍历可一次穿透所有层级，返回带标签的结构化内容，适合快速了解未知页面的完整结构。
    - 跨站 iframe（支付、登录、嵌入的第三方组件）在另一个进程里，父页面读不到它的 `contentDocument`，选择器点击也进不去。先 `/frames` 列出页面的 iframe（按 id、name、网址或顺序认出目标，取 `frameId`），再 `/eval?frame=` 在其中执行（隔离环境，共享 DOM，看不到页面的 JS 变量）；`/clickXY` 按视口坐标点中其中的元素，会逐层进入嵌套的 iframe。字段与坐标换算见 [API 参考](references/cdp-api.md)。
    - `/scroll` 到底部会触发懒加载，使未进入视口的图片完成加载。提取图片 URL 前若未滚动，部分图片可能尚未加载。
    - 拿到媒体资源 URL 后，公开资源可直接下载到本地后用读取；需要登录态才可获取的资源才需要在浏览器内 navigate + screenshot。
    - 短时间内密集打开大量页面（如批量 `/new`）可能触发网站的反爬风控。
    - 平台返回的"内容不存在""页面不见了"等提示不一定反映真实状态，也可能是访问方式的问题（如 URL 缺失必要参数、触发反爬）而非内容本身的问题。
    
    ### 视频内容获取
    
    用户浏览器真实渲染，截图可捕获当前视频帧。核心能力：通过 `/eval` 操控 `<video>` 元素（获取时长、seek 到任意时间点、播放/暂停/全屏），配合 `/screenshot` 采帧，可对视频内容进行离散采样分析。
    
    ### 登录判断
    
    用户日常浏览器天然携带登录态，大多数常用网站已登录。
    
    登录判断的核心问题只有一个：**目标内容拿到了吗？**
    
    打开页面后先尝试获取目标内容。只有当确认**目标内容无法获取**且判断登录能解决时，才告知用户：
    > "当前页面在未登录状态下无法获取[具体内容]，请在你的浏览器中登录 [网站名]，完成后告诉我继续。"
    
    登录完成后无需重启任何东西，直接刷新页面继续。
    
    ### 任务结束
    
    用 `/close` 关闭自己创建的 tab，必须保留用户原有的 tab 不受影响。
    
    保留 Proxy 持续运行，不主动停止或设置退出计时器。下一次任务先运行前置检查，再复用已有连接。
    
    Proxy 的自动清理只针对通过 `/new` 创建且闲置 15 分钟的标签页，不会退出服务或关闭用户原有标签页。重启服务或浏览器后，浏览器可能要求重新授权 CDP 连接。
    
    ## 并行调研：子 Agent 分治策略
    
    任务包含多个**独立**调研目标时（如同时调研 N 个项目、N 个来源），鼓励合理分治给子 Agent 并行执行，而非主 Agent 串行处理。
    
    **好处：**
    - **速度**：多子 Agent 并行，总耗时约等于单个子任务时长
    - **上下文保护**：抓取内容不进入主 Agent 上下文，主 Agent 只接收摘要，节省 token
    
    **并行 CDP 操作**：每个子 Agent 在当前用户浏览器实例中，自行创建所需的后台 tab（`/new`），自行操作，任务结束自行关闭（`/close`）。所有子 Agent 共享一个浏览器、一个 Proxy 和一条 CDP 连接；并发请求在发现、握手阶段也共用一次连接尝试，不按 Agent 分别发起授权。同一 tab 的操作仍需协调，通过不同 targetId 分配任务。服务维护会影响全体 Agent，应在任务完成后集中执行。
    
    **子 Agent Prompt 写法：目标导向，而非步骤指令**
    - 必须在子 Agent prompt 中写 `必须加载 web-access skill 并遵循指引` ，子 Agent 会自动加载 skill，无需在 prompt 中复制 skill 内容或指定路径。
    - 子 Agent 有自主判断能力。主 Agent 的职责是说清楚**要什么**，仅在必要与确信时限定**怎么做**。过度指定步骤会剥夺子 Agent 的判断空间，反而引入主 Agent 的假设错误。**避免 prompt 用词对子 Agent 行为的暗示**：「搜索xx」会把子 Agent 锚定到 WebSearch，而实际上有些反爬站点需要 CDP 直接访问主站才能有效获取内容。主 Agent 写 prompt 时应描述目标（「获取」「调研」「了解」），避免用暗示具体手段的动词（「搜索」「抓取」「爬取」）。
    
    **分治判断标准：**
    
    | 适合分治 | 不适合分治 |
    |----------|-----------|
    | 目标相互独立，结果互不依赖 | 目标有依赖关系，下一个需要上一个的结果 |
    | 每个子任务量足够大（多页抓取、多轮搜索） | 简单单页查询，分治开销大于收益 |
    | 需要 CDP 浏览器或长时间运行的任务 | 几次 WebSearch / Jina 就能完成的轻量查询 |
    
    ## 信息核实类任务
    
    核实的目标是**一手来源**，而非更多的二手报道。多个媒体引用同一个错误会造成循环印证假象。

    class Engine:
        def __init__(self, config, store, session, clock, progress=print):
            self.config, self.store, self.session, self.clock = config, store, session, clock
            self.progress = progress
    
        def validate(self, kind, validator, raw, *args):
            try:
                return validator(raw, *args)
            except ProtocolError as exc:
                exc.diagnostic.update(stage="validation", request_kind=kind)
                self.store.set("last_protocol_error", {"at": self.clock.now(), **exc.diagnostic})
                raise
    
        def preflight(self):
            self.session.gate.preflight()
            if self.store.next_identity_job() is not None:
                return
            if self.config.stage == "formal" and (self.config.reviewed_notes < 10 or self.store.complete_count() < self.config.pilot_notes):
                raise StopRun("pilot_review_required")
            if self.store.complete_count() >= self.config.collection_limit:
                raise StopRun("pilot_complete_review_required" if self.config.stage == "pilot" else "target_reached")
            day = local_day(self.clock.now(), self.config.timezone)
            if self.config.quota_mode == "daily" and self.config.daily_notes is not None and self.store.count_daily_notes(day) >= self.config.daily_notes and not self.store.next_note(day, self.config.daily_notes):
                raise StopRun("daily_note_limit")
    
        async def discover(self):
            job = self.store.link_refresh_job()
            refresh = job is not None
            if not refresh and self.store.pending_count() >= self.config.candidate_low_watermark:
                return False
            if not refresh:
                job = self.store.next_keyword(self.config)
            if job is None:
                return False
            if refresh and job["refresh_attempts"] >= 1:
                self.store.mark_note(job["note_id"], "needs_review", "link_refresh_exhausted", self.clock.now())
                return True
            raw = await self.session.call("search", lambda: self.session.adapter.search(job["keyword"], job["page"], job["search_id"], job["sort"]),
                                          key=job["keyword"] + ":" + str(job["page"]))
            items, has_more = self.validate("search", search_page, raw)
            if refresh:
                self.store.refresh_links(job, items, self.clock.now())
            else:
                self.store.add_search_page(job, items, has_more, self.clock.now(), self.config.sampling_version)
            self.progress("候选发现完成；详情与评论按队列限额处理。")
    
            return True
    
        async def run(self, already_ready=False):
            self.store.prepare_identity_backfill(self.clock.now())
            self.preflight()
            self.store.register_keywords(self.config)
            if not already_ready:
                await self.session.ensure_ready()
            try:
                discovered_once = False
                while True:
                    self.preflight()
                    if await backfill_step(self.store, self.session, self.clock, self.progress, self.validate):
                        continue
                    day = local_day(self.clock.now(), self.config.timezone)
                    next_note = self.store.next_note(day, self.config.daily_notes if self.config.quota_mode == "daily" else None)
                    if not self.config.continuous_daily and len(self.session.gate.run_notes) >= self.config.notes_per_run and (next_note is None or next_note['note_id'] not in self.session.gate.run_notes):
                        raise StopRun("per_run_note_limit")
                    discovered = False
                    if not discovered_once or next_note is None:
                        discovered = await self.discover()
                        discovered_once = True
                    day = local_day(self.clock.now(), self.config.timezone)
                    note = self.store.next_note(day, self.config.daily_notes if self.config.quota_mode == "daily" else None)
                    if note is None:
                        if discovered:
                            continue
                        raise StopRun("no_pending_candidates")
                    note_id = note["note_id"]
                    try:
                        if note["state"] == "pending":
                            raw = await self.session.call("detail", lambda: self.session.adapter.detail(note_id, note["token"], note["source"]), note_id)
                            self.store.save_detail(note_id, self.validate("detail", note_detail, raw, note_id), self.clock.now())
                        raw = await self.session.call("comments", lambda: self.session.adapter.comments(note_id, note["token"], note["cursor"]), note_id, note["cursor"])

                        self.progress("已保存一页评论；完成笔记数：%s" % self.store.complete_count())
                    except Unavailable:
                        self.store.mark_note(note_id, "unavailable", "note_unavailable", self.clock.now())
                    except StaleLink:
                        self.store.mark_note(note_id, "needs_link", "link_expired", self.clock.now())
            except ProtocolError:
                self.store.pause(self.clock.now(), "protocol_error")
                raise

## Assistant

**目前是把关键词提交给小红书搜索接口，使用平台返回的搜索结果；程序没有指定“只匹配正文”“只匹配 tag”或“模糊匹配”。** 所以，tag 与搜索关键词不一致，并不一定是采集错误。

具体过程是：

1. 将 `config.json` 中的每个关键词分别提交给搜索接口，默认使用综合排序 `general`。
2. 将返回的帖子加入候选队列，并按帖子 ID 去重。
3. 获取标题、正文、tag 和评论，**目前不会再检查这些字段是否实际包含搜索词**。

因此，需要区分两个字段：

| 字段 | 含义 |
|---|---|
| 来源关键词 `sources.keyword` | 用哪个词搜索时发现了这篇帖子 |
| 帖子标签 `tags` | 该帖接口返回的话题标签 |

例如，用“母乳喂养”搜到一篇帖子，其正文讨论母乳喂养，标签却是“新手妈妈”“育儿日常”，这两者并不矛盾。**但若标题、正文、标签都没有检索词，当前程序也会保留它。** 仅凭我们的代码无法确定平台为什么返回该帖，也不能据此断言平台采用了某种模糊或语义匹配算法。

对于你的研究，我建议把**“平台检索发现”与“研究相关性筛选”分开**：保留原始检索结果，再为每篇帖子标记关键词是否出现在标题、正文、标签中；三者都未命中的帖子进入待核查列表。这样既能检查检索偏差，也不会因为 tag 不一致就误删相关内容。

论文中当前方案可以准确写为：**“使用主题关键词进行平台检索，合并去重后形成候选帖子集。”** 暂时不宜写成“按标签精确匹配”或“正文关键词匹配”。
